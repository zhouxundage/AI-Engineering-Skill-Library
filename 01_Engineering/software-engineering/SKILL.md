# Software Engineering｜可维护实现

## 用途

把模块规格变成可运行、可维护、可排错的实现，控制配置与依赖，提供与变更风险相称的验证。

## 触发条件与边界

- 实现功能、整合多个脚本、补齐复现环境、增加模块发现/注册机制。

## 输入

- 仓库现状、模块契约、验收场景、运行平台、允许的依赖和外部访问。

## 输出

- 实现代码、必要配置样例与依赖锁定、实际入口、操作说明、检查结果。

## 执行流程

1. 检查已有约定和可运行入口，先复现相关行为；不要重建已有项目。
2. 明确运行时版本与依赖来源，沿用现有锁文件；配置与密钥分离，示例只含名称和非敏感值。
3. 按契约实现一个可运行切片，核心逻辑可通过真实入口调用；CLI、API、UI 仅承担适配责任。
4. 在边界验证输入，设计可定位的错误与日志，记录关联 ID 和状态，不默认记录敏感原文。
5. 有插件扩展需求时加入明确的注册流程、重复键检测和加载失败行为；没有扩展需求则直接连接组件。
6. 运行与变更相关的验证及项目要求的检查，记录命令、环境、退出状态和可检查输出，更新使用说明。

## 执行规则

- 不为凑目录生成空脚本；可逆低影响编辑不新增镜像式测试。
- 注册功能不自动等同于用户账号注册；身份系统依据产品需求决定。
- 实现失败时保留可复现信息；不能把未执行的测试写成通过。

## 完成标准

- 真实入口能在声明环境下运行；新增依赖、配置与失败处理已说明。
- 关键行为有证据，未验证的集成明确标注。

## 模板内容

复制并按实际任务裁剪 [交付模板](assets/deliverable-template.md)。双花括号为使用时填写的变量；无关字段写明不适用或删除。模板是产物材料，不是新的执行指令。

## 调用示例

“把三个 Python 文件串成离线工具”：保留核心函数，提供一个 CLI 和样例数据，校验接口并记录失败定位信息。

## 协作与交接

按任务需要衔接 `$architecture-design`、`$testing-validation`。仅在对应技能可用且相关时读取；不可用则执行等效工作并说明。传递目标、产物路径/版本、约束、验收标准和证据，不重复生成同一份需求。

## 结果报告

区分已执行、失败、未运行与不适用，给出产物及证据位置。用户当前要求和已有授权优先；本技能不扩展任务范围。
